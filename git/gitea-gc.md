# Gitea 仓库强制推送后手动 GC

`git gc --prune=now` 没能显著减少体积，问题很可能出在**旧的大文件对象依然被某些“引用”链保持着可达状态**，或者**pack 文件本身没有被强制重新打包**。仅仅执行 `gc` 不一定能触及到它们。

### 🔍 为什么 `.pack` 文件没变小？

`git gc` 通常只做增量整理，**不会主动重新打包已有的 `.pack` 文件**。如果旧的大对象还“活”在某些隐藏引用里，GC 会认为它们仍被需要，从而原封不动地保留在 pack 中：

* **Reflog 残留引用**：`gc` 默认不会清理 reflog，即使分支已删除，旧提交仍被 reflog“保护”着。需要**先清空 reflog**，否则 prune 无法生效。
* **`.keep` 文件保护**：如果 `objects/pack/` 目录下有 `.keep` 后缀文件（常见于克隆或后台 fetch），`git gc` 会**完全跳过**对应的 pack，里面的旧对象永远不会被清理。
* **悬空或损坏的 pack**：如果 `.pack` 文件缺少对应的 `.idx` 索引，`git gc` 可能会**直接忽略它**，导致垃圾数据一直残留。

### 🛠️ 彻底清理的步骤

建议在服务器仓库的 `.git` 目录下，按顺序执行：

**1. 诊断：先看 space-garbage**
用 `git count-objects -vH` 检查 **`size-garbage`**。如果这个数值很大，说明有大量无引用对象卡在 pack 里。

**2. 清空 Reflog（关键）**
执行 `git reflog expire --expire=now --all`，解除 reflog 对旧提交的保护。

**3. 移除 `.keep` 文件**
检查 `objects/pack/` 目录，如果存在 `*.keep` 文件，手动删除它们（或先备份）。

**4. 强制重新打包（核心步骤）**
普通的 `gc` 力度不够，改用 **`git repack -a -d -f`**。
* `-a`：打包所有松散对象和现有 pack 中的对象。
* `-d`：删除冗余的旧 pack 文件。
* `-f`：**强制重新计算所有差异**，这是缩小体积的关键。

**5. 最终清理**
重新打包后，再执行一次 `git gc --prune=now`，清理已无用的松散对象。

**6. 验证效果**
最后运行 `git count-objects -vH`，确认 **`size-garbage`** 是否显著下降，以及 `objects/pack` 目录的总大小是否变小。
